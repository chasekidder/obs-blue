# Phase 7: claim highlighting and deck warnings

Date: 2026-11-24
Branch: `improve/7-seller` (base: `improve/6-camera-audio`)
Switches: `[claim_highlight] enabled` and `[deck_warnings] enabled` (both default `false`)

## Claim highlighting

- **Rule** (`stream_pilot/claims.py`): a comment is a claim if it starts with a number (optionally after `#` or `$`), contains at least two numbers (digits, optionally with decimals or a fraction: `3.00`, `2/1.00`), and is at most 80 characters. That covers `21 cookie sheets 3`, `26blue 7`, `$5 crew mens#31`, `#31$house$3`, `18 $6 x mas wreath`, `55 4 teal`, `6 resess X2 $3`, `45 penguin gift tags 2/1.00`, `10- hat 3.00`, and leaves out `55 how much`, `6 sure`, `20 goodnight everyone`, `Hi Penny`. Guessing-game entries (`21 40 miles`) and bids (`55 5500`) match; a false highlight is harmless.
- **In the page:** the same patterns are rendered into `fb/watcher.js`. After each debounced pass the watcher classifies every comment article by its extracted text (the author is not part of it) and adds or removes the class `sp-claim`; one `<style id="sp-claim-style">` gives it a yellow background and a left bar. A node is re-checked when its text length changes; the class is re-applied if React drops it.
- **Capture unchanged:** the MutationObserver watches child lists only, not attributes, so adding a class triggers nothing, and the extraction never reads classes. The pinning style and the hidden "Minimize comments" button are separate and untouched.
- **Off:** the rendered watcher has `CLAIM_HIGHLIGHT = false` and returns before touching the page.
- **Tests:** `test_claims.py` (the listed shapes), browser tests in `test_comments_browser.py` with invented names (highlighted exactly the claims; the record equals the posted comments; pinned; minimize hidden; survives a React re-render; off adds nothing), the rendered script passes `node --check`.

## Deck warnings

On the spare key (index 4), in READY, LIVE and RECONNECTING, the first that holds:

1. **`MIC?`**: the microphone's peak stayed below `mic_silent_db` (-70 dB) for `mic_silent_s` (30 s). Levels come from OBS's `InputVolumeMeters` event, subscribed only while this switch is on (OBS sends it every 50 ms; the handler looks at one every 0.5 s). Before Go Live a holding scene keeps the microphone off the air, and OBS then reports no level for it: not a warning. While live, no level at all counts as silence.
2. **`CAM?`**: a camera listed in `[deck_warnings] cameras` (default `["main"]`; the close-up camera's device is commented out on the PC, so checking it by default would always warn) has no device node, or its OBS source points at a missing device, or it is on air and OBS says its source is not active. Checked every 10 s.
3. **`NET`**: `GetStreamStatus` every 2 s; a sample is bad if more than `net_skipped_pct` (1 %) of its frames were dropped or OBS's congestion was above `net_congestion` (0.3). `NET` shows when at least 80 % of a `net_window_s` (20 s) window is bad. The known single 10 s burst (75 frames) covers half the window and never trips it (test); a sustained problem does, and it clears once the window is good again.
4. **`MEM`**: the memory guard's warning. With this switch on, the guard is handed the warnings object instead of the deck, so `MEM` is just the lowest priority; in other states only `MEM` is shown, as today.

Warnings never block going live: they are a background loop (2 s, each step bounded) started only while the switch is on, plus a synchronous state hook. Off: no subscription, no loop, and the memory guard drives the key as today.

**Cost measured on the PC** (READY, 60 s, `CPUUsageNSec` of stream-pilot.service): 0.82 % of one core with deck warnings on, 0.32 % with them off.
